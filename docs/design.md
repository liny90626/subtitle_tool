# 技术选型与设计说明

## 1. 需求与约束

- Windows 桌面小工具，导入任意视频，生成对应字幕文件
- 自动识别音轨语种；视频含多条不同语言的音轨时能选轨
- 字幕目标语言可选（即需要机器翻译，不能只做转写）
- 性能与稳定性优先；离线可用，不依赖用户自行安装 FFmpeg

## 2. 方案调研

### 2.1 语音识别

| 方案 | 优势 | 不选的原因 |
| --- | --- | --- |
| **faster-whisper**（CTranslate2） | 同精度下比原版快约 4 倍，内存占用更低；**不依赖 PyTorch**；wheel 自带 PyAV(内置 FFmpeg) 与 Silero VAD；99 语种 | — **已选** |
| openai/whisper（原版） | 参考实现，生态最广 | 依赖 PyTorch，单是运行时就 2GB+，打包体积不可接受；速度最慢 |
| whisper.cpp | 无 Python 依赖，跨平台二进制小 | 需要自己做绑定或子进程调用，进度/取消/逐段语种检测都要重写；多音轨选轨也得自己接 FFmpeg |
| WhisperX | 强制对齐后时间戳最准，还带说话人分离 | 依赖 PyTorch + pyannote，体积与复杂度翻倍，且模型许可需要额外接受条款 |
| NVIDIA Canary / Parakeet | 英语等少数语种 WER 更低 | 语种覆盖远不如 Whisper，与「多国语言」的需求正相反；依赖 NeMo 生态 |

选 faster-whisper 的决定性因素是**不引入 PyTorch**：这让 Windows 免安装包能控制在
500MB 上下，而不是 3GB 起步。

### 2.2 音频解码与多音轨

faster-whisper 自带的 `decode_audio()` 用 PyAV 解码，但写死了 `container.decode(audio=0)`
——只认第 0 条音轨。多语言片源常见的「国语/粤语/英语」多音轨场景直接用不了。

因此自行实现 `audio.py`：用 PyAV 列出全部音轨（编解码器、声道、语言标签、标题），
按指定序号解码为 16kHz 单声道 float32。帧处理沿用 faster-whisper 里经过验证的做法
（跳过损坏帧、AudioFifo 攒批后重采样、手动 GC 释放重采样器缓冲）。

用 PyAV 而不是调用 ffmpeg.exe：PyAV 的 wheel 内置 FFmpeg 库，用户不需要另外安装、
配 PATH，打包时也不用附带外部可执行文件。

### 2.3 翻译

| 方案 | 不选的原因 |
| --- | --- |
| **NLLB-200-distilled-600M**（CTranslate2 int8） | — **已选**：单个模型覆盖 200 语种的任意方向，620MB；与语音识别共用 CTranslate2 运行时，不引入第二套推理框架 |
| Whisper 自带 `task=translate` | 只能翻成英语，无法满足「选择目标语言」 |
| Opus-MT / Argos Translate | 按语言对分模型，多语种音轨要下载多个模型；argostranslate 依赖 stanza，又把 PyTorch 拽回来了 |
| 在线 API（DeepL / Google） | 质量最好，但需要密钥且必须联网，与离线可用冲突 |

分词没有用 `transformers`，而是直接用 `tokenizers` 读模型仓库里的 `tokenizer.json`，
手工拼 NLLB 的输入格式（`[源语言码] 子词… </s>`，目标语言码作解码前缀）。
`tokenizers` 本来就是 faster-whisper 的依赖，这样翻译功能**零新增依赖**。

### 2.4 界面与打包

- **PySide6**：原生拖拽、QThread 信号槽做后台任务、表格控件直接放下拉框。相比
  Tkinter 省掉拖拽外挂库；相比 Gradio 不用起浏览器和本地服务。
- **PyInstaller onedir**：单文件模式每次启动都要把几百 MB 解压到临时目录，冷启动十几秒
  且杀毒误报率高，因此用单目录免安装包。

## 3. 关键实现决策

这几条都是实测踩出来的，不是预先设计的。

### 3.1 字幕条按词级时间戳重新切分

`BatchedInferencePipeline` 比顺序推理快，但它把 VAD 切出的整块语音当成一条结果输出，
实测 60 秒素材只出 2 条、每条 30 秒近 300 字符——写进 SRT 完全没法看。顺序推理的分段
好一些，但仍会出现 12~18 秒的长条。

两种管线的词级时间戳质量实测一致（同一素材 154 vs 155 个词，时间戳逐词对齐）。
因此保留批量推理的速度，打开 `word_timestamps=True` 后自行切分：

- 词间静音 > 0.7 秒断开（说话人换气/换句的天然分界）
- 句末标点且已够 12 字符时断开
- 字数（两行）或时长（7 秒）超限时兜底断开，且**回退到后半段最近的标点**
  ——否则「…do for your | country.」会把最后一个词甩成单独一条字幕
- 切出的短条延长到至少 1.2 秒（按每秒约 15 字符的阅读速度，0.4 秒的字幕来不及看）

### 3.2 翻译前按句、再按子句切分

NLLB-600M 是句级模型。实测 20 token 以上的多子句句子会**整段漏掉后半句**：

```
输入  And so my fellow Americans ask not what your country can do for you,
      ask what you can do for your country.
整句  所以我的同胞们，不要问你们的国家能为你们做些什么。      ← 后半句没了
拆句  所以我的同胞们不要问你们的国家能为你们做些什么，问你能为你的国家做些什么。
```

换 beam size、length penalty、repetition penalty 都复现，是模型本身的问题。因此翻译前
先按句末标点拆句，单句仍超过 20 token 就按子句标点继续拆，译完再拼回。
拆句判定避开了 `3.5`、`Dr. Smith` 这类假句末。

**没有**为了凑行数把字幕条切得更短：试过让双语排版按单行长度切分，结果每条只剩半句，
翻译模型拿到残缺片段，译文碎成「本软件的副本和相关」这种读不通的短语。译文连贯比少
一行重要，已回退。

### 3.3 CJK 标点还原

NLLB 对中日文目标语一律输出 ASCII 标点（`所以,我的同胞们.`）。按目标语种换回全角，
且只在**前一个字符是汉字/假名**时替换，避免误伤 `3.5`、`Dr. Smith`。

### 3.4 多语种音轨的逐段语种

faster-whisper 的 `multilingual=True` 会逐窗口重判语种并切换解码提示词，但
`Segment` 上**不带**语种字段，翻译时拿不到每段的源语言。因此转写后按约 30 秒一组
回看原始波形补测语种，组内共享结果——逐段测太贵（每次要跑一遍编码器，而字幕条常常
只有几秒）。

### 3.5 默认模型跟着设备走

同一段 60 秒素材，8 核 CPU、int8：

| 模型 | 转写耗时 | 相对实时 |
| --- | --- | --- |
| `base` | 6.4s | 9.34× |
| `small` | 22.0s | 2.72× |
| `large-v3-turbo` | 83.2s | 0.72× |

`large-v3-turbo` 在 CPU 上慢于实时，做默认值会让 1 小时的视频跑 80 多分钟，
而免安装包默认就是 CPU 推理。因此启动时用 `ctranslate2.get_cuda_device_count()`
探测显卡：有 GPU 默认 `large-v3-turbo`，没有则默认 `small`。

### 3.6 模型下载：缓存优先，官方源连不上就换源

打包版实测最常见的失败不是识别或翻译出错，而是**根本下不到模型**。识别与翻译模型都
托管在 huggingface.co，这个域名在国内多半连不通，huggingface_hub 会一路超时到
`ConnectTimeout: [WinError 10060]`，最后抛出来的却是「cannot find the appropriate
snapshot folder」——看着像程序坏了，其实只是网络到不了下载源。

因此把「取模型」从 faster-whisper / huggingface_hub 手里接管过来（`hub.py`），做三件事。

**缓存优先。** huggingface_hub 即使缓存命中也要先问一次 Hub 有没有新版本，网络不通就
得等满超时。模型仓库是固定不动的，所以先用 `local_files_only=True` 试一次，三个必备
文件（`config.json` / `model.bin` / `tokenizer.json`）齐了就直接用——下过一次之后完全
不联网，也才算兑现了「离线可用」。少文件说明上次下到一半，当作没有重下。

**换源前先探测，而且要探对东西。** 只测「连得上」不够：hf-mirror.com 对境外 IP 会 308
跳回 huggingface.co，而 huggingface_hub 不跟随跨域跳转，这种源看着通、实际下不动。
因此按它真正依赖的东西判定——HEAD 一个小文件，响应头里必须带 `x-repo-commit`。探测走
huggingface_hub 自己的 HTTP 客户端，与真正下载共用同一套代理和证书设置。两个源都探不过
时仍按首选源试一次：探测只用来加速选源，不该把本来能下的情况直接挡掉。

**换源要能穿透到已经导入的 huggingface_hub。** 它在 import 时就把 `HF_ENDPOINT` 读成
模块常量，0.x 的 `file_download` 还把 URL 模板按名字绑了过去，只改 `constants` 上那一份
不管用。所以设置分两路生效：包一被导入就先写环境变量（赶在 huggingface_hub 之前），
界面上临时改则扫一遍已导入的模块改常量，并把 HTTP 连接池丢掉重建（代理是建连接池时读
环境变量的）。非官方源还要额外关掉 Xet——它的分块下载会绕开镜像，直连 huggingface 自己
的存储服务器，连不上官方源的网络照样下不动。

### 3.7 中英双语：拿中文原文当查表的键

界面和命令行都要出中英两套文案。没有用 Qt 的 `.ts`/`.qm`：那套要在打包流程里多挂
`lupdate`/`lrelease` 两个步骤，而且只管 Qt 界面，命令行的帮助和报错还得另想办法。

改成一个 Python 字典，**中文原文直接当键**：

```python
t("载入模型 {model}…", model="small")
```

源码里一眼看得出会显示什么，不用另发明 `MSG_LOADING_MODEL` 这类 key，缺译文时自动
退回中文，界面和命令行共用同一套。代价是改中文原文会让译文悄悄失效，所以
`tests/test_i18n.py` 用 AST 扫一遍源码逐条核对：每处待翻译的中文都得有译文、译文里的
`{占位符}` 要和原文完全一致（漏一个就是运行时 KeyError）、表里也不许留没人用的旧条目。

两条约定：**变量一律走占位符**，不在外面拼 f-string，否则查不到表；阶段名
（「语音转写」这些）在流水线内部当字典键用，只在显示前才 `t()`，免得换语言把进度回调的
键也换掉。

切语言不重开窗口：每处文案在创建时用 `_text` / `_live` 登记一次，切换时把登记过的重新
渲染一遍——文件列表、选好的目标语种、填过的输出目录都留在原处。99 种语种名在
`languages.py` 的表里中英各存一列，跟着界面语言走，`--target` 两种写法都认。

### 3.8 其它

- `condition_on_previous_text=False`：长视频一旦出现幻觉会以上文为条件自我强化成复读，
  牺牲少量上下文连贯性换稳定性
- SRT 写 UTF-8 BOM（Windows 上不少播放器靠它认编码），VTT/TXT 不写
- 音轨语言标签同时认 ISO 639-2 的 B/T 两套写法（`ger`/`deu`）和 BCP-47 两字母写法（`zh-CN`）
- 进度回调按 0.5% 步进节流：解码是逐帧回调的，不节流会打爆 Qt 事件队列

## 4. 已知限制

- **翻译质量上限**取决于 NLLB-600M。长句、专业术语、口语梗的译文一般般；换 1.3B 模型
  会好一些但慢 2 倍以上。追求质量应该导出原文字幕后用在线大模型翻译。
- **不做说话人分离**，多人对话不会标注谁在说话。
- **整轨解码进内存**：16kHz float32 单声道约 每小时 230MB，4 小时的片源要 ~1GB 内存。
- **GPU 需要另装 CUDA 运行库**，免安装包只带 CPU 推理（见 README）。
- 逐段语种检测按 30 秒分组，同一组内换语言会跟着组内多数走。
- 界面只做了中英两种语言；语种名、报错和帮助都随之切换，但**已经写进日志的行不会重译**。
- **自动换源会把下载请求发到第三方镜像** hf-mirror.com（只取公开的模型权重，不涉及
  用户的视频或字幕）。不接受的话把「模型下载」锁到官方源即可。
